# FYP 伪沙盒平台需求与框架草案

日期：2026-10-09（Asia/Hong_Kong）  
状态：根据用户需求整理的设计提案；未实现，未验证。引擎与交互界面形态均未锁定。

## 1. 当前确定与尚未确定

用户已表达的目标：围绕已有玩法 prototype，构建 AI-assisted rapid greyboxing / level-design 工具及其 methodology；保留多种玩法，支持描述、直接编辑、试玩、修改；让创作者能调试自己的关卡，并产出可演示体验。

2026-10-09 用户明确补充：交互界面未必融合到游戏里。游戏内 built-in、引擎编辑器工具、独立工具接入游戏等形态都可考虑，不能把其中一种写成已确认方向。先完善需求和产品框架，之后再评估 Unity / UE 等引擎。

本文件将“调试”暂按关卡创作者的需求定义：找出设计、配置和实际运行的问题，定位对象或区域，修改后快速复测。任意用户脚本编程、通用游戏代码调试暂不作为默认范围。

## 2. 产品定位

一个允许创作者在规定玩法与编辑边界内，通过 AI 和手动操作设计、试玩、调试、迭代关卡的伪沙盒系统。

“伪沙盒”的工作定义是受约束的创自由，不是已经确认的学术分类：玩法模板提供可玩的基础规则，创作者调整关卡结构、对象和允许的参数。每种模板分别说明什么能改、什么受保护、怎样测试。

创作者是使用工具制作关卡的人；玩家是体验该关卡的人。同一个人可以切换角色，但两种界面不必是同一个界面。首阶段可先由 TianXi 自己作为创作者，其他用户的目标能力和使用环境仍待确定。

## 3. 一条完整的创作与调试流程

选玩法模板 → 试玩示例、了解规则 → 建立关卡草稿 → 描述意图或直接编辑 → 检查候选修改 → 应用 → 试玩 → 查看问题及定位 → 局部修改 → 从起点/检查点复测 → 保存版本。

场景例子（设计提案）：创作者希望“第二段更有挑战，但保留第一段”。AI 给出局部修改，创作者检查并应用。试玩时在同一处失败几次；系统显示失败位置和当时相关对象/参数。创作者可以手动调整，也可以请求 AI 提出修改；再次试玩并决定保留或撤销。重复失败只是观察，不自动证明关卡坏了。

试玩入口可以是游戏内切换、引擎 Play、外部工具启动测试程序；具体入口随交互形态决定。

## 4. 需要具备的能力

| 能力 | 创作者需要完成什么 | 首个可用版本建议 |
| --- | --- | --- |
| 玩法模板 | 选择已有玩法、理解控制与胜负条件、试玩示例 | 一个验证模板；保留后续扩展为多种玩法的结构 |
| 关卡编辑 | 放置、选择、移动、复制、删除对象，调整允许的参数 | 少量对象；先做位置与关键参数，再按需要扩展旋转/缩放 |
| 受控自由 | 明白规则、可编辑范围和受保护内容 | 每模板独立定义对象清单、参数范围与固定规则 |
| AI 协作 | 表达设计意图、让 AI 理解当前状态并做局部修改 | 一个可靠的局部修改任务，支持查看变化、应用/取消和撤销 |
| 试玩 | 用真实控制器、碰撞和胜负逻辑体验关卡 | 能启动、停止、重新开始；编辑状态不被试玩临时状态污染 |
| 调试反馈 | 知道哪里出了问题、回到对象或区域修改并复测 | 开始前配置检查；试玩中的失败位置、完成结果与必要事件 |
| 版本与作品管理 | 保存、重开、恢复旧版本、继续编辑 | 本地保存/加载及撤销；检查点版本随后加入 |
| 可演示体验 | 向他人展示创作过程及可玩结果 | 一个贯通的例子；之后增加第二种玩法展示复用能力 |

这些是建议验收范围，不是已完成的功能或用户已逐项确认的范围。

## 5. 把“调试自己的关卡”拆成三种问题

### A. 可以确定的配置问题

例如缺少起点/目标、对象引用失效、参数越界、起点处于检测到的障碍内。依据实际实现的检查规则阻止启动或给出明确错误，并关联到相关对象。没有实现的检查不能宣称已经覆盖。

### B. 需要提示和试玩的设计问题

例如跳跃间距可能过大、障碍过密、引导不清、目标不明显。系统可以给警告、显示相关参数，并建议复测；不能仅凭几何距离或 AI 判断保证不可通关、可通关或好玩。

### C. 运行时观察到的问题

记录与该模板有关的事件，例如落点、死亡/失败原因、检查点、目标触发、耗时。事件与对象 ID、关卡版本对应，供创作者回看和定位。首版不默认收集完整录像、全部输入轨迹或第三方用户身份。

反馈流程应包括：问题 → 相关位置/对象 → 依据 → 可选修改 → 应用/取消 → 重试。AI 要区分系统测到的事实和自己的解释；例如“在这里失败 3 次”是记录，“原因可能是跳距过大”是待验证解释。

### 预设阈值与生成前检查（2026-10-09 用户新增需求）

用户希望把间距等预设范围放入 schema，让系统在生成前读取规则、发现超范围意图并提醒用户。该需求已纳入框架；以下字段和分级是实现提案，具体数值尚未测定。

- 每个模板/控制器配置包含可编辑属性、单位、建议阈值、允许范围、适用条件、规则版本和依据。跳跃间距需要定义测量口径，例如两个平台最近边缘的水平距离，不能混用中心点距离。
- 建议阈值用于难度/体验警告；模板允许范围用于限定该模板开放的设计范围；角色能力限制只有在相关条件和依据充分时才用于更强的可达性诊断。超过建议阈值不等于物理上不可通过。
- 示例数值（纯示意，非实测）：普通同高跳跃的建议间距不大于 3 米，该模板允许间距不大于 4 米。3.5 米提示超过建议；4.5 米提示超过当前模板允许范围。允许上限是设计边界，不能仅凭此把“超范围”写成“确定无法通关”。
- 如果用户意图已包含明确数值，先检查请求再生成；如果只有“更难一点”等描述，先生成候选关卡数据，计算派生值，再在应用到场景前检查。两者都不需要先将有问题的内容写入正式关卡。
- AI 读取 schema/rules 以减少无效生成；程序用同一规则确定性地检查结果。JSON Schema 可以表达部分字段范围，跨对象间距、空间重叠等计算由检查程序完成，不能只靠提示词。
- 反馈包含对象/区域、实际值、阈值、单位、原因、适用条件及处理选项。例如“平台 A→B 间距 4.5 米，超过当前模板允许的 4 米；缩短间距，或加入中间落点”。建议范围可允许用户确认后继续试验；严格模板范围是否可覆盖需由模板策略明确定义。
- 阈值必须跟随角色移动/跳跃、重力、平台高差、移动平台及辅助机制变化。条件不匹配时标记规则不适用/需复测，不能沿用旧阈值作绝对结论。测试中成功达到的最大距离也不能直接当作物理极限。
- 修改后再次检查；保留用户已保护的内容。AI 不得为了消除警告而未经用户意图许可改变角色能力或玩法规则。

验收建议：同一规则在 AI 候选生成、手动编辑和应用前检查中结果一致；消息能定位相关对象；未知/不适用的条件有明确提示；改变控制器配置后不继续使用失效的检查结果。整体通关性与趣味性仍需试玩评价。

## 6. 界面形态保持开放

| 候选 | 创作界面在哪里 | 试玩与反馈怎么往返 | 需要验证的核心问题 |
| --- | --- | --- | --- |
| 游戏内 built-in | 游戏自带创作界面 | 游戏内切换或启动测试，再回到编辑状态 | 打包程序能否编辑/保存；AI 接口及操作体验是否可实现 |
| 引擎编辑器工具 | 引擎插件、面板或已有编辑界面 | 引擎 Play/Test，反馈回到创作工具 | 创作者是否需要安装并学习引擎；改动能否验证和撤销 |
| 独立工具接入 | 单独的创作程序或网页界面 | 通过数据/操作接口启动或连接目标游戏，返回运行反馈 | 数据与状态一致性、连接恢复、对象定位和保存路径 |

允许混合方案，例如外部面板控制一个本地测试程序；是否值得实现必须通过小样验证，不默认混合越多越好。

本轮不锁定用户需安装什么、发布为独立程序还是引擎工具、是否有浏览器界面或游戏内 AI。选形态时考虑目标创作者、FYP 时间、展示方式和实测工作量。

## 7. 功能框架，不先绑定界面或引擎

创作入口（位置待定）
  → 关卡操作与历史（读取、选区、编辑、应用、撤销、保存）
  → 关卡内容与模板规则
  → 游戏执行部分（载入、运行、重置、真实玩法）
  → 检查与试玩事件
  → 反馈到创作入口，继续修改

AI 通过受控的关卡操作参与；直接编辑也使用同样的验证规则。一次失败不能留下半个修改，也不能让重试重复生成同一个对象。

建议保留五项最小接口约定：读取关卡、应用一组改动、启动/停止测试、获取测试反馈、保存/恢复。它们是功能约定，不强制使用 MCP、网络服务或某一种文件格式。

实现责任：
- 模板负责该玩法的控制、规则、对象类型、允许参数、起点/目标和相关事件。
- 关卡内容记录模板/格式版本、对象稳定 ID、摆放、参数及规则配置。
- 试玩状态记录角色状态、计时、失败等临时信息；不直接覆盖设计文件。
- 检查负责已明确规则；AI 提供候选改动和解释，不能代替引擎真实测试。
- 界面负责让创作者选择、理解、控制和修正操作；具体承载位置未决定。

不是同时开发 Unity 和 UE 两套运行端。先用同一份小测试任务评估候选，再实现一条运行链路。

## 8. AI 的开发用途与产品用途

开发阶段：Codex/agent 可以通过引擎工具或 MCP 协助搭场景、写代码和检查结果。

产品阶段：创作者使用描述功能时，系统需要把关卡状态、选区和限制提供给 AI，再验证其建议，反馈操作结果。它可以在游戏内、引擎工具或外部工具中实现。

开发 MCP 能操作编辑器，不等于最终用户已经能在产品里描述、编辑和试玩。如果产品选编辑器工具形态，编辑器集成可以是交付路径；如果选独立游戏内/外部工具形态，还须验证对应的运行程序接口。

## 9. 开始制作的阶段顺序

1. **明确首条用户任务**：例如创建一条路线，试玩发现一处问题，局部修改并保存。确定第一模板、可编辑对象、反馈事件和最小作品用途。
2. **做界面/流程小样**：画或制作能走通上述任务的简单演示；比较 built-in、引擎工具或外部工具的必要步骤。不必三种都完整开发。
3. **做技术 spike、再选引擎**：候选执行同一小场景与任务，测试内容读写、一次编辑、真实试玩、问题反馈、保存重开及撤销。采用所选界面需要的运行环境验证，记录版本、设备、耗时和人工步骤。
4. **先完成手动闭环**：创作者不用 AI 也能编辑、试玩、定位问题、修改、保存和重开。
5. **接入 AI**：先实现一个局部编辑任务；读取实际状态、检查结果、撤销失败修改。不要先承诺任意文本生成完整游戏。
6. **扩展第二种玩法并准备展示**：检查共用功能是否可复用，同时保留不同控制器与规则。评价是否缩短迭代过程、保留创作者控制并减少修补成本。

## 10. 验收场景与范围

建议最小完整演示：创作者建立关卡 → 手动改一处 → 真实试玩 → 看到一条与对象对应的问题反馈 → 手动或 AI 局部修改 → 撤销一次不满意的修改 → 再试玩 → 保存 → 重开获得同一关卡。

需要记录：每步实际是否完成、修改是否只发生在允许区域、失败是否可解释和恢复、重开结果是否一致、实际耗时。快速、低门槛和好玩仍是待评价的目标，不是设计文档已经证明的结论。

账号、多人联机、公共作品市场、任意脚本、任意现有游戏导入、跨引擎完整兼容、自动通关证明和云端同步均不作为本次框架的首版前置条件；以后按实际目标决定。

## 11. 下一次需要收敛的决定

- 创作者：先服务自己/会使用引擎的人，还是完全不了解引擎的用户？
- 第一玩法模板及其可编辑边界、需要反馈的事件。
- 作品先在系统内保存和试玩，还是需要独立导出？
- 三种界面形态中先验证哪一种；运行时 AI 是否是该形态首版的必要能力？
- 据上述任务的 spike 结果选择具体引擎和完整版本。

当前原有 UE 优先候选记录作为参考保留，但不能替代这次产品形态与实际任务的验证。

## 12. 开工前的架构与 Asset 准备顺序（2026-10-11 建议）

整体能力和模块责任已经整理；首个玩法模板、对象编辑边界、最终界面形态、模型接口与部分实现细节仍待收敛。它是可开始做小样的框架，不是已经验证的完整技术架构。

建议先做一条可玩的最小流程，同时建立共用基础：载入少量关卡数据 → 用占位物体生成场景 → 手动改对象 → schema/空间规则提示 → 真实试玩并返回一条反馈 → 保存并重开。先覆盖这条流程所需能力，再根据第二模板抽取共用部分。

Asset 分为两类：
- **玩法基础**：玩家控制器、碰撞、相机、胜负逻辑以及必要的交互对象。优先复用用户已有 prototype；其工程/位置本轮尚未取得。如没有，则先做最简单控制器。选择后才能校准移动/跳跃能力和 schema 阈值。
- **视觉与展示资源**：角色模型、环境、装饰、材质、动画、音效。首阶段用立方体、平面、胶囊等占位，流程通过后按具体缺口挑资源，并验证尺度、碰撞、所选渲染管线与版本兼容。

第一阶段可以采用临时测试面板或操作入口，最终 built-in、编辑器工具或外部界面依然开放。AI 与手动编辑面向同一套受控操作/检查；创作者关卡数据继续与试玩临时状态分开。

当前建议不要求用户先搜集大批素材，也不把仅搭目录/抽象接口当成平台已经完成。真正的第一里程碑是一段可编辑、可试玩、可反馈并保存的关卡。
