### 助手

你的顾虑成立，而且它本身就是 ① 比 ② 强的理由：在 ① 里，**你造的是系统，AI 只是系统里的一个部件**——技术价值在你这边，panel 一眼能看出来。

「② 用 ① 实现」的意思跟你猜的一样：底下有一个你（用 AI 工作流）做好的游戏作为**基底**，展上观众通过一个 agent 现场改它——改关卡、改规则、改敌人行为——改完立刻能玩。观众体验到的是"AI 在做游戏"，但不是从零生成（从零生成现场必翻车），而是在一个你定义好的空间里改。

如果走这条路，你的技术工作实际上是这四块，每一块都是你的，不是 AI 的：

| 模块 | 你要做的决定 | 为什么这是研究 |
|---|---|---|
| **设计空间** | AI 能改什么、不能改什么——一个 schema/DSL，不是让它自由写代码 | 这是整个项目的核心命题：co-creation 的边界怎么画 |
| **现场回路** | 观众说话 → agent 规划 → 校验 → 热更新到浏览器，延迟控制在 10–30 秒 | 工程主体，Three.js 是唯一现实的栈 |
| **失败处理** | AI 生成垃圾/越界时怎么办：校验、回退、还是把失败也展示出来 | 展上必然发生，处理方式本身是设计 |
| **过程可视化** | 观众能看到 agent 在想什么、调了什么——这才是"体验 AI 做游戏的过程" | 不然观众只看到结果，和 ② 没区别 |

还有一个可选但很值的设计：**累积世界**——每个观众的修改留在游戏里，展览三天结束时那个游戏是几百个人和 AI 一起改出来的。这比"每人从头玩一次"有意思得多，也给你一个天然的分析对象。

两个后果要接受：
1. **原来的双路线对比彻底关掉。** Unity+MCP 做不了给观众用的现场热更新，连 pilot 都没必要了。文献换成 mixed-initiative co-creativity（Yannakakis / Liapis 那条线）+ LLM 游戏生成（Rosebud、造化工坊公开资料）。
2. **游戏的问题没消失，只是变小了**：基底得是一个 2 分钟内好玩、参数改了立刻看得出来的小核心循环。如果观众改完感觉不到区别，装置就死了。

所以现在的问题从"想做什么游戏"变成：**观众改的是什么？** 给三个例子帮你想——
- 跑酷/平台关卡：观众描述"我想要更多陷阱、跳台更远"，AI 重排关卡
- 塔防/波次：观众设计下一波敌人的行为
- 物理玩具箱：观众加规则（"球碰到红色会分裂"），AI 写成规则

哪一类是你自己会想上手改的？

## Three.js 是不是 browser-only？

不是"只能在浏览器"，是"只要有 WebGL/WebGPU 上下文就能跑"：浏览器、Electron/Tauri 桌面壳、Unity 里嵌的 WebView（Vuplex）、UE 的 WebBrowser widget 都行。**但它永远不会成为 Unity/UE 的渲染器**——引擎有自己的渲染器，Three.js 在引擎里最多是贴在一张纹理上的网页。所以"在引擎里用 Three.js"字面意义上答案是否；有意义的问法是：**引擎和 web 栈怎么分工，才能各拿各的长处。**

三个问题分开答，都用同一个例子：**一个灰盒平台跳跃关卡**。

## 1. Web build 不是"打成 Three.js"

Unity Web build = Unity 把**它自己的引擎**（C# 编译成 WebAssembly + Unity 自己的渲染器跑在 WebGL/WebGPU 上）塞进一个网页。浏览器里跑的就是 Unity，Three.js 完全不出现。网页只是一个壳，壳里有一个 `<canvas>` 是 Unity 在画，壳的其他部分（聊天框、agent 的思考过程、按钮）是普通网页。

```
浏览器页面
├── <canvas>  ← Unity 引擎在这里跑（你在 Unity 编辑器里做的游戏，原样）
└── 网页部分  ← 聊天框 / agent 调用 / 过程可视化（普通 HTML+JS）
       │
       └── unityInstance.SendMessage("LevelLoader", "Apply", jsonString)
                                       ↑ 把一段 JSON 递给 Unity 里的某个脚本
```

所以"两边都用上"的意思是：**游戏本体和物理是 Unity 的，围着它的 agent 层是 web 的。**

## 2. Schema = "AI 能改的东西的清单，写成固定格式"

不是让 AI 写代码，而是让 AI 填一张表。表长什么样、有哪些格子、每格能填什么范围——这就是 schema。例子：

```json
{
  "platforms": [
    { "x": 0,  "y": 0, "width": 4 },
    { "x": 6,  "y": 2, "width": 3 },
    { "x": 11, "y": 1, "width": 2 }
  ],
  "hazards": [ { "type": "spike", "x": 8 } ],
  "player": { "jumpHeight": 3, "speed": 5 },
  "goal": { "x": 14, "y": 2 }
}
```

规则（也是 schema 的一部分）：platform 最多 12 块、`jumpHeight` 在 2–5 之间、任意两块平台间距不能超过 `jumpHeight`+1……

观众说"我想要更多陷阱、跳台更远"，agent 输出的**只是一份新的 JSON**。它不碰 Unity 代码，改不坏游戏，最坏情况是 JSON 不合规——被校验拦下来，回退到上一版。

这就是为什么之前说"设计空间是核心命题"：**schema 里放什么、不放什么，就是你在决定观众和 AI 的创作边界。** 放 `jumpHeight` 进去，观众能改手感；不放，观众只能改布局。这个取舍是研究，其余是工程。

## 3. Adapter = "把 JSON 变成引擎里的东西"的那段代码

| | Unity adapter | Three.js adapter（如果做 stretch） |
|---|---|---|
| 是什么 | 一个 C# 脚本 `LevelLoader.cs`：读 JSON → 清空场景 → 按 `platforms` 生成方块 → 摆 hazards → 设玩家参数 | 一个 JS 函数：读同一份 JSON → 生成 `BoxGeometry` → 加到 scene |
| 输入 | 同一份 JSON | 同一份 JSON |
| 大小 | 一两百行 | 一两百行 |

Adapter 是薄的，因为重活（物理、碰撞、渲染）引擎自己干。这也是为什么"一个 schema、两个后端"的成本不是 ×2——schema、agent、校验、UI 全部共用，只有这一两百行要写两遍。

```
add_platform(x, y, width)
set_jump_height(value)     // 只接受 2–5

```

| | JSON schema | MCP 工具面 |

| 塔防 / 波次 | ✓ | △ 一波 1–2 分钟 | ✓ | △ | ✓ | △ 要懂规则 | ✓ |
| 物理玩具箱 | ✓ | ✓ | △ 规则难写成参数 | ✗ | ✓ | ✓ | ✓ |
| 推箱子类解谜 | △ | ✓ | ✓ | ✓ 可用求解器 | ✓ | △ 要动脑 | ✗ 旁观无聊 |

**前两名是平台跳跃和迷你高尔夫。** 平台跳跃好检查，迷你高尔夫门槛更低。

还有一个跟类型无关、但可能比类型更重要的点：**一人出题，一人闯关。** 观众 A 跟 AI 说"给我朋友做一关最坑的"，观众 B 上去玩，大家看 B 翻车。这一下就把它从"一个工具"变成了"一个游戏"——正好回应 Kim 说的 entertainment。今天可以拿这个问他。

## 四个词

**Schema = 菜单。** 观众和 AI 只能点菜单上有的菜，份量也有范围（"辣度 1–5"）。菜单上写了"跳跃高度"，观众就能改手感；没写，就只能改布局。**菜单上写什么，就是你的研究问题。**

**Adapter = 厨房。** 把点菜单变成真的菜。同一张单子可以送进 Unity 厨房，也可以送进 Three.js 厨房。厨房各自写一两百行代码，菜单共用。

**Stretch = 加分项。** 主线做完还有余力才做的东西。这里指"再加一个 Three.js 厨房，同一句话两边并排出菜"——你原来的两路线对比从这里回来。

**Contingency = 退路。** proposal 评分里"Evidence of planning"那 25% 明确要求写：计划出问题时怎么办。我之前说"stretch 写进 contingency"说得不准——stretch 是往上的，contingency 是往下的。两者的关系是：进度落后时，第一个被砍的就是 stretch，这本身就是一条退路。这个项目该写的退路大概是：

| 出了什么问题 | 退路 |
|---|---|
| 现场网络 / API 挂了 | 预先生成一批修改缓存在本地，或退化成几个预设按钮 |
| AI 生成不合法的关卡 | 校验拦下，回到上一版 |
| 开发进度落后 | 先砍 Three.js adapter（stretch），再砍"累积世界" |

三点见 Kim，带着"平台跳跃 vs 迷你高尔夫"和"一人出题一人闯关"去问，比空着手问"我该做什么游戏"好得多。

换个你肯定熟的东西来说：**schema 就是这个游戏关卡的"捏脸系统"。**

捏脸界面里有"眼睛大小 0–100""发型 20 选 1""肤色色盘"。你能捏出千奇百怪的脸，但捏不出三只眼睛——因为根本没有那个滑块。**决定有哪些滑块、每个滑块能拉多远的人，是设计师。**

schema 就是这件事，只不过：滑块是给关卡的，拉滑块的是 AI，观众只负责说话。

## 跑酷的 schema 可能长这样

| 能改的东西 | 能怎么改 | 规则 |
|---|---|---|
| 障碍 | 类型：栏杆 / 火车 / 坑；放在哪条道、第几米 | 同一位置三条道不能全堵死 |
| 坑 | 宽度 1–4 格 | 宽度 ≤ 当前跳跃距离 |
| 跳板 | 放在哪 | 只能放在坑前面 |
| 金币 | 位置、数量 | 最多 50 个 |
| 速度 | 慢 / 中 / 快 | — |
| 主题皮肤 | 霓虹 / 森林 / 城市 | — |

这张表就是 schema 的全部。它是一份**你写的文件**，AI 和程序都读它。

## 它具体做了三件事

**1. 告诉 AI 能做什么。** AI 拿到的不是"随便改游戏"，而是这张表。它只能在表里挑。

**2. 检查 AI 做得对不对。** AI 提交修改后，程序按"规则"那一列逐条检查。

**3. 告诉 Unity 怎么搭。** 检查通过的修改，Unity 照着表的格式读，按部就班把关卡搭出来。

## 走三个观众的请求

| 观众说 | AI 想做 | schema 的反应 |
|---|---|---|
| "中间加个大坑" | 中间道放一个宽 3 的坑 + 前面放跳板 | 宽 3 ≤ 跳跃距离，通过 ✓ |
| "再加一个更大的坑" | 放一个宽 6 的坑 | 超过跳跃距离，**拦下**，告诉观众"这个跳不过去" ✗ |
| "加一条喷火的龙" | 表里没有"龙" | **根本没有这个滑块**。AI 只能说做不了，或者换成最接近的：一列火车 |

图里那条灰色的"想加第二个坑，被拦下：跳不过"，就是第二行在屏幕上的样子。

## 没有 schema 会怎样

让 AI 直接写 Unity 代码。观众说"加条龙"，AI 可能真去写一段龙的脚本——然后编译报错、游戏卡死、下一个观众来的时候屏幕是黑的。三天展期里这会发生很多次。

## 为什么说它是你的研究

因为表里放什么，全是取舍：

- 放了"速度"，观众能改手感；不放，就只能改布局

## 关键区别：schema 限制的是"零件"，不是"成品"

你说的"选配料放碗里"是麻辣烫：观众自己挑，挑完就是结果。这里不一样——schema 规定的是**有哪些零件**，但零件怎么组合，空间大得离谱。

跑酷一关 1000 米、三条道，每一米都可以放或不放障碍、放哪种、放哪条道。零件只有五六种，能拼出来的关卡数是天文数字。这更像乐高：积木只有那几种，能搭什么没有限制。

**观众不挑零件，观众说感觉。把感觉变成几十个零件的具体摆法，这就是模型要思考的。**

## 同一句话，菜单和模型的差别

观众说："给我朋友做一关最坑的"

| | 菜单（按钮） | 大模型 |
|---|---|---|
| 做法 | 点"难度 = 最高" | 自己设计"坑"是什么 |
| 结果 | 满屏障碍，密得没法玩，一点也不好笑 | 前 10 秒故意很简单让人放松 → 一排金币把人引到右道 → 金币尽头是一列火车 → 跳板跳起来落点正对栏杆 |
| 用的零件 | 一样 | 一样 |

两边用的零件一模一样，但右边那关有**设计**：节奏、诱导、反预期。这是模型在想的东西。

## 模型具体在做的几件事

1. **把模糊的感觉翻译成具体摆法**："像在逃命"→ 逐渐加速、障碍越来越密、金币越来越少
2. **安排节奏**：难的地方前面给喘息，陷阱前面放诱饵
3. **记得上下文**："比刚才那关再难一点，但别太离谱""撤销那个坑，金币留着"
4. **被拦下时协商**："坑太宽跳不过，要不我把跳板挪近一点？"
5. **表里没有的东西找替代**："加条龙"→ 用一列从后面追上来的火车代替

## 但你的担心在一种情况下是对的

如果 schema 只有"难度、速度、主题"这种粗滑块，那模型确实没用，几个按钮就够了，还更快。

所以 schema 要**细到零件级别**（每个障碍放哪），模型才有价值。但越细，模型出错的机会越多，校验越难。

**这恰恰就是你的研究问题**：schema 粗了，AI 是多余的；细了，AI 有用但容易翻车。那个平衡点在哪、为什么在那——就是论文要回答的东西。

**1. 最成功的三款关卡制作游戏，用的是同一条规则：作者必须先自己通关。** 马里奥制造、几何冲刺、Trackmania 全都这样。这就是上次清单里"校验很难做"那个洞的现成答案——你的展台也可以这么定：**做完的关卡，你得自己过一次才能挂上展厅墙。** 自动检查只需要拦住明显坏掉的，剩下的交给这条规则。而且它本身是个好玩法：你想坑朋友，先得证明你自己过得去。

## 一、游戏本身

| 项 | 设定 | 为什么 |
|---|---|---|
| 视角 | 2D 横版，方块角色自动往右跑 | 旁观的人一眼看懂 |
| 操作 | **只有一个键：点一下 = 跳** | 零门槛。不做"按住跳更高"，那会让校验变难 |
| 跳跃 | 固定弧线：高 2 格，远度随速度变（慢 3 格 / 中 4 格 / 快 5 格） | 确定性，后端能精确算出"跳不跳得过" |

| 一关长度 | 60–200 格，中速下 10–35 秒 | 一局 ≤ 2 分钟，死几次也够 |
| 胜利 | 碰到终点旗 | — |
| 美术 | v0 纯灰盒 | 先验证好不好玩，皮肤以后加 |

世界是**网格**：横向按格子算位置，纵向 0–5 层。这是为了让"能不能过"可以被程序精确判断。

## 二、Schema v0：六种零件

一关由 3–12 个**段落**顺序拼成，每段 8–20 格长，零件放在段落里。用段落而不是整条赛道，是为了让 AI 能按"节奏"思考（这段难、下段喘口气），也让观众能说"把第三段改一下"。

| 零件 | 参数 | 范围 | 作用 |
|---|---|---|---|
| **坑** | 位置、宽度 | 宽 1–4 格 | 最基本的障碍 |
| **方块** | 位置、宽度、高度 | 宽 1–4，高 1–2 | 台阶；也是爬上高层的垫脚 |
| **尖刺** | 位置、数量、放在哪 | 1–3 个一排；地面 / 方块顶 / 平台上 | 碰到就死 |
| **弹跳板** | 位置 | — | 跳得更高更远（高 4 格，远 1.5 倍） |
| **高层平台** | 位置、宽度、高度、**会不会塌** | 宽 2–8，高 3–4；塌 = 踩上 0.5 秒后掉落 | 形成上下两层路线，陷阱的关键 |
| **金币** | 位置、高度、数量 | 高 0–5，1–5 个一排 | 诱饵：把人引到你想让他去的地方 |

另外两个全局设置：**速度**（慢 / 中 / 快）、**关卡名**。

注意高层平台 3–4 格高，而正常跳只有 2 格——**所以上层路线只能靠"方块垫脚"或"弹跳板"上去**。零件之间有了依赖，AI 才有东西要设计。

## 三、规则（校验）

光有范围不够。坑宽 4 格在范围内，但中速下跳不过去。所以还需要规则：

| # | 规则 | 管什么 |
|---|---|---|
| R1 | 零件不能重叠、不能超出段落 | 结构正确 |
| R2 | **从起点到终点至少存在一条能过的路** | 程序模拟所有起跳时机，找得到就算过 |
| R3 | **每次起跳至少有 2 格的时机窗口** | 难度下限。路过的观众不是几何冲刺玩家，不能要求帧级操作 |
| R4 | 第一段前 8 格必须是空地 | 开局不能直接死 |
| R5 | 总长 60–200 格，零件总数 ≤ 80 | 一局的时长 |

R3 是这版 schema 里最重要的一条设计决定：它就是"观众友好"这件事写成了规则。按这个算，中速下不借弹跳板的坑最宽只能 2 格——**范围写的是 1–4，实际能用多宽取决于速度和有没有弹跳板**，这正是 AI 要去权衡的。

通过校验后还会算一个**难度星级**（按每 10 格需要跳几次、窗口平均多宽），显示给观众。

发布规则（不在 schema 里，是产品规则）：**做关卡的人必须自己通关一次，才能挂上展厅墙。**

## 四、AI 能调用的工具

schema 对 AI 来说就是这组工具。每调用一次，右边"AI 做了什么"就多一行：

```
add_section(after, length)                        加一段
remove_section(section)                           删一段
place(section, part, params)                      放零件
edit(section, item, changes)                      改零件参数
remove(section, item)                             删零件
set_speed(slow | normal | fast)
check()          → 返回违反了哪条规则，AI 可以先自查
submit(summary)  → 交给校验；不过就退回原因，最多重试 3 次
```

### 助手

专业策划不会先想"做什么功能"，而是先回答几个问题，再让所有功能都去服务答案。放到你的项目上，大概是这样一套考量：

## 1. 先定"情绪高点"

策划最先问的是：**玩家在哪一秒最爽？** 其他所有设计都为那一秒服务。

你的项目里，最爽的不是"做出一关"，而是**看着朋友死在你设的陷阱上**。那一下的笑声才是展台最吸引人的东西。所以要反推设计去放大它：

- 朋友死的那一刻，屏幕标出"死于 ×× 设的陷阱"
- 通关结束后自动回放朋友最惨的一次死亡
- 展厅墙上显示每关"坑死了多少人"

## 2. 定三条设计支柱

支柱是用来**砍需求**的。每个新想法都拿来对一下，对不上就不做。建议是：

| 支柱 | 意思 | 它会砍掉什么 |
|---|---|---|
| **一句话就有变化** | 说完十几秒内必须看到关卡变了 | 要观众打很长一段话的功能 |
| **坑得公平** | 死了能看懂自己为什么死，心里想"被你坑了"而不是"这不讲理" | 没有预兆的陷阱、需要帧级操作的难度 |
| **做给别人看** | 每个关卡都是为了给另一个人玩 | 只能自己玩、不能分享的东西 |

## 3. 逐项过一遍专业维度

| 维度 | 专业策划会问 | 放到你的项目上 |
|---|---|---|
| **玩家是谁** | 谁在玩、在什么场景下、有多少时间 | 路过的人，通常两三个结伴来，停留 3–5 分钟。设计单位是"一小群人"，不是一个人 |
| **核心循环** | 玩家重复做的那件事是什么 | 做关 → 自己通关 → 给朋友玩 → 看他死 → 再改。第二个循环：挑墙上别人的关来玩 |
| **前 30 秒** | 路人多快能开始玩、多快尝到甜头 | 最大的问题是"空白页"：观众不知道说什么。要有示例提示、从一个种子关卡开始改，而不是从零 |
| **手感** | 操作舒不舒服、死了多快能重来 | 死亡后 0.5 秒内重来（像《超级食肉男孩》）。另外要加"土狼时间"（离开平台后短暂还能起跳）——**这个会影响校验，后端模拟时必须算进去** |
| **关卡语法** | 好关卡有什么结构 | 任天堂的"起承转合"：先介绍一个零件 → 加难度 → 来个反转 → 收尾。这正好可以写进 AI 的设计知识 |
| **公平陷阱** | 坑人和恶心人的界线在哪 | 陷阱要有预兆：会塌的平台要有裂纹、尖刺不能藏在屏幕外。这可以直接写成 schema 规则 |
| **内容生态** | 玩家内容多了怎么办 | 墙上三天后会有几百关，烂关会淹没好关。需要排序："坑死最多的""最多人挑战""今日推荐" |
| **等待时间** | 系统慢的时候玩家在干嘛 | 见下面第 4 点 |
| **吞吐量** | 一小时能服务多少人 | 一次做关 3–5 分钟 → 一个工位一小时十几个人。建议两个工位：一台做关，一台只玩墙上的关 |
| **成功标准** | 怎么知道它成功了 | 提前定指标：多少人做完并发布、墙上的关平均被玩几次、第一次尝试死在哪 |

## 4. 三个最有价值的专业做法

**把等待变成表演。** AI 改关卡要 5–20 秒，这是体验上最大的坑。专业的处理不是加个转圈的加载图标，而是**让零件一块一块掉进关卡里**——AI 每调用一次工具，画面上就落下一个零件。等待本身变成了看点，旁观的人也看得懂 AI 在干嘛。

**先做"绿野仙踪测试"。** 在写任何 AI 代码之前，你自己扮演 AI：朋友对着电脑说"给我加个坑"，你躲在后面手动改关卡数据。半天就能测出这个项目最核心的问题——**"说话做关卡"这件事到底好不好玩**。如果连真人扮演的 AI 都不好玩，接了真的 AI 也救不回来。这是专业团队在昂贵开发之前的标准动作。

**先做垂直切片，再铺开。** 一关、六个零件、打磨到手感和反馈都对，比十几个零件都粗糙要强得多。你的 v0 计划已经是这个思路。

## 最该马上做的

1. **定情绪高点和三条支柱**——今天就可以定，后面所有取舍都靠它
2. **绿野仙踪测试**——半天，验证核心假设
3. **v0 可玩版**——验证手感

绿野仙踪测试这周就能做，而且它本身就是很好的 sketchbook 材料：照片、朋友说了什么、哪里卡住了。

## 做多种游戏，但不用做 N 个游戏

Kim 担心的是"每种游戏都是一个完整的游戏"。解决办法是瓦里奥制造 DIY 的思路：**不做 N 个游戏，做一套能互相拼的玩法积木。**

| 积木类别 | 可选项 |
|---|---|
| 镜头 | 横版滚动 / 俯视 / 固定一屏 |
| 主角怎么动 | 自动往前 / 方向键自由移动 / 只能左右 |
| 按键干什么 | 跳 / 往上冲 / 开火 / 变向 |
| 场上会出现什么 | 障碍 / 追你的敌人 / 从天上掉的东西 / 子弹 |
| 怎么赢 | 到终点 / 活够 N 秒 / 收集 N 个 / 打掉所有目标 |
| 节奏 | 越来越快 / 波次 / 固定 |

同一套积木，拼法不同就是不同的游戏：

| 游戏 | 拼法 |
|---|---|
| 一键跑酷 | 横版 + 自动往前 + 按键跳 + 障碍 + 到终点 |

## 这样一改，好几个问题同时变好了

- **AI 不再只是更快的编辑器**：它在设计玩法，这才是真的"做游戏"
- **研究问题更有意思了**："非专业的人要做出感觉真不一样的小游戏，最少需要几块积木？"

这个流程里，AI 的工作已经比较明确：**把设计意图转换成具体内容，并持续处理局部修改。** 用户始终可以接管。

有几个容易被前面的“聊天框 + 引擎”结构漏掉的环节，需要补上。

**第一，AI 必须知道“现在是什么样”。**  
它不能只记得聊天历史。你手动移动了一个平台、删了一个障碍之后，下一次请求必须带上当前关卡、选中的对象，以及你指定不能改的部分。否则就会出现：你刚调好的东西，被 AI 又改回去了。

因此，界面、AI 和引擎应围绕**同一份关卡数据**工作。Schema 规定这份数据的格式；检查程序判断修改是否可接受；引擎根据数据还原场景。这三者要分别实现，schema 文件自己不会检查“好不好玩”。

**第二，生成和修改要有明确的操作边界。**  
例如你选中第二波，再说“简单一点”，默认应该只改第二波。整关重做要有明确入口。AI 的修改先形成草稿，通过检查后再应用，并支持整次撤销。这样直接编辑和对话才能舒服地并存。

**第三，试玩反馈需要回到设计现场。**  
返回编辑时，至少保留刚才测试的是哪个版本、你在哪结束或失败。后面可以再加死亡位置标记。难度曲线则适合作为辅助信息，但最初只能叫“估计的压力曲线”，不能把障碍数量直接当成真实难度。

**第四，保存是最低要求，导出决定工具的用途。**  
“只能在工具里玩”“能导出独立可玩作品”“能回到引擎项目继续开发”，对应三种不同的交付承诺。这个必须提前选。

我建议把下面这些作为下一轮定调清单：

| 要定的事 | 我的建议起点 | 为什么 |
|---|---|---|
| **主要服务谁** | 想做关卡、但不想处理引擎细节的人；你自己也是用户 | 决定界面要简化到哪一步 |
| **模板来源** | 先支持你制作并接好的 prototypes | “任意导入一个游戏就能编辑”会增加大量适配工作 |
| **第一组玩法** | 从跑酷、俯视躲避、迷你高尔夫中选；至少包含两种明显不同的体验 | 保住你要的选择空间，也能检验方法是否能跨类型使用 |

| **编辑深度** | 选中、移动、旋转、复制、删除、改参数、局部对话、撤销 | 这是你能真正接管 AI 的最低功能集合 |

其中我最想先明确的是**模板来源**。它和 Kim 说的“基于已有 prototype”直接对应：你可以总结出一套接入方法——一个 prototype 要提供哪些可编辑对象、参数、操作和试玩入口，接好以后就能通过统一界面快速设计内容。这样，methodology 有具体内容，工具也能被你实际使用。

**选玩法模板 → 先玩懂它 → 描述意图 → 生成草稿 → 局部编辑 → 试玩反馈 → 继续修改 → 保存与使用。**
